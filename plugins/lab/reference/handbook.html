Start here

Eight hours, four modules, one plugin you keep

This is a training in AI fluency: going from understanding how AI agents work to building a full AI system that does real, complex work. You build it yourself, on your own machine, and you take it home.

Three commands

1. Make an empty folder and open VS Code in it

$ mkdir ~/agent-lab && cd ~/agent-lab && code .

The lab needs its own folder — it becomes a git repository holding your checkpoint commits. Don't open VS Code in your home directory or an existing project.

2. Add the marketplace and install the tutor

In the Claude Code panel:

/plugin marketplace add Ravl-io/agent-lab-marketplace
/plugin install lab@agent-lab

If the install summary says Run /reload-plugins to activate, run that.

3. Start

/lab:start

That orients you, shows the curriculum, lists what you need installed, checks your machine, and asks which track you're on. It's also the command you run at the start of every session to pick up where you left off.

Accept the trust prompt

Claude Code shows a trust dialog the first time you open a folder. Until you accept it, the project's permission settings are ignored and every tool call stops to ask you for approval. If you see "Ignoring N permissions.allow entries… this workspace has not been trusted", that's this.

How the lab runs

You type. The tutor coaches.

This is the working agreement. It's short, and the first line is the one that matters.

The learning contract

The tutor explains, reviews, unblocks, quizzes and grades. It deliberately will not write your work for you — if it did, you'd leave with something you can't maintain and no idea how it works.

Being stuck is not a failure state. /lab:hint gives a nudge rather than a solution, and getting unstuck is the part that teaches. If you ask outright for the answer, the tutor will show you the shape of it and leave the interesting decisions to you.

Every block runs the same five beats

FrameWhy this exists — what broke in the step before
BuildYou type. The tutor coaches, the facilitator floats
RunYou see the real output, or the real score
NameNow the concept gets its name, and its limits
GateA checkpoint: your work is validated and saved

Concepts arrive after you've felt the problem they solve. If something feels frustrating just before a concept lands, that's the design working, not you failing.

Checkpoints, and never being stranded

Each module has several checkpoints. At each one your work is validated by a real check — not a tick-box — and committed, so it survives between sessions and across machines.

If something breaks badly, or you fall behind the room:

/lab:catchup

That replays the lab's own files — settings, the tracer, the experiment runner — and repairs anything deleted or broken, without touching your work. Adding --with-reference also drops in the reference solution, which is the rescue for someone genuinely stranded.

Not cheating

Catchup exists so one bad pip install or a mistyped rm can't cost you a module. Use it without embarrassment. The only thing it costs you is the learning from the exercise it skipped, which is why the tutor will offer you a hint first.

The gates are real

A checkpoint that only records progress isn't a gate. Each one runs a script that checks behaviour:

GateWhat it actually checks
check_intent.pyThe five sections, and that Open questions isn't empty
check_skill.pyFolder and frontmatter names match, description long enough to trigger, no TODOs, body has real structure
check_tool.py--selftest passes with at least three checks, stdout is valid JSON, the agreed keys are present
check_hook.pyIt's registered under PreToolUse, then five payloads are fed to it to see what it decides
check_plugin.pyComponents are in the plugin, paths are portable, claude plugin validate passes

Each reports specific problems, and each distinguishes blocking failures from "worth improving". A note is your next iteration, not a mistake.

Module 01 · two hours

Harness and coding agentReady

By the end you should be able to answer, out loud, to a colleague: what is an agent, what is the harness made of, and which primitive do I reach for?

The ladder

You climb a ladder where each rung exists because the one below it broke.

RungWhat it fixesWhat's still wrong
PromptGets a result, onceNot repeatable, not shareable
User-invoked skill
a "command"		A repeatable, versioned promptCan't act; can't guarantee anything
ToolDeterministic action, structured outputThe agent doesn't know when to use it
Model-invoked skillThe agent decides when, from the descriptionIt can still skip it
HookEnforcement the model can't bypassNot distributable on its own
PluginPackages all of it, installable, versioned—
One primitive, two invocation modes

Rungs 2 and 4 are the same file format, one frontmatter line apart. disable-model-invocation: true makes it yours to type; leaving it off makes the description a trigger. You'll write one, then turn it into the other.

The lab, step by step

05 min

Setup

Five files and nothing else: settings.json, a tracer hook, and an experiment runner with its first prompt. No data yet — setup is incremental on purpose, and each stage adds only what the next experiment needs.

Checkpoint M1.C0-setup
110 min

What is an agent?

Three runs of the same thing, differing in one flag. Read .claude/lab-trace.log after each — hook output isn't shown in the session, which is why it goes to a file you open.

$ python3 experiments/exp.py 1   # --tools ""
$ python3 experiments/exp.py 2   # --tools "Read"
$ python3 experiments/exp.py 3   # --tools "Read,Write"

With no tools, the model answers the general question well and says plainly that it cannot know what your ticket is. One call, zero tool requests. Then you give it Read:

--> SENT TO THE MODEL your prompt <-- BACK FROM THE MODEL it wants a tool: Read(file_path=…) --> HANDED TO THE HARNESS (the model is paused, waiting) <-- RESULT SENT BACK 1,247 chars of the file <-- FINAL ANSWER what the ticket is about This experiment: 2 call(s) to the model, 1 tool request(s).

The model didn't read the file. It asked. The result went back in, and the model ran again — so an agent is not a model, it's the loop.

Checkpoint M1.C1-agent
210 min

The core tools, and their limit

Read, write, execute, search files, search the web. Almost everything an agent appears to do decomposes into those five. Then you hand it all of them and ask for your real job, with no procedure at all.

$ python3 experiments/exp.py 4
Expect it to do well

A capable model with good data does this job well. That's not the problem being solved, and you won't be told otherwise. What's wrong is elsewhere: it spent its opening turns running find and ls to work out where your data lives, it invented its own output shape rather than the one your team reviews, and it will do all of that differently next time.

Tools give capability. They don't carry procedure — the order you work in, the checks that must happen before a conclusion, the format your colleagues review. That gap is what a skill fills: not making bad work good, but making good work repeatable.

2b8 min

Intent

You've just watched an agent do your job well and in the wrong shape. Now write down the right shape. This is the kickoff artifact from Anthropic's AI-native SDLC playbook — in real work it comes first, in place of a backlog entry and a refinement meeting.

Don't fill it in alone. The tutor interviews you about scope, users, constraints and what success looks like, drafts intent.md from your answers, and you correct what it got wrong. The words stay yours; that's the point of the artifact.

SectionWhat it's forWhere it lands
ProblemWhat's wrong today, in your wordsWhat you check the result against
Proposed outcomeWhat's true once this existsModule 4's acceptance criteria
Affected users and systemsWho touches it, what it reads and writes — and what it deliberately doesn'tScope, and the write boundary in step 5
ConstraintsThe rules it must work withinYour skill's constraints and your hook
Open questionsWhat you don't know yetThe list you take to your team
Don't leave Open questions empty

It's the section people skip and the one that costs. An unwritten question gets silently answered by whoever implements it, usually wrongly and usually without anyone noticing. The gate refuses an empty one.

Keep the whole file under about 40 lines. In step 6 it gets imported into CLAUDE.md with a line reading @intent.md, which puts it in context on every turn — the difference between intent that shapes the work and intent that sits in a file nobody opens. Every line is then paid for on every turn.

Checkpoint M1.C2-intent
320 min

Skills

A skill is a folder with a SKILL.md in it. What makes it different from a document is when it loads:

LevelWhat it isWhen the model sees it
1The description in the frontmatterEvery turn, alongside the tool definitions
2The body of SKILL.mdOnly once the model decides to activate it
3Files the body points atOnly if the procedure needs them

That's progressive disclosure. The model sees a one-line menu of everything available, so a skill that isn't used costs one line. You write yours from a scaffold, starting from the Constraints section of your intent — the first time an earlier artifact pays for itself.

Then you run the same prompt as step 2, with the skill available, and read the trace:

<-- BACK FROM THE MODEL Skill(skill='triage-ticket', args='CASE-4471') …the model chose it. Nobody typed a slash command. <-- RESULT SENT BACK {"success": true} …the body is NOT in the trace. The harness injects it as context. <-- BACK FROM THE MODEL Read(data/examples/triage-note-example.md) <-- BACK FROM THE MODEL Read(data/knowledge/triage-policy.md) …level 3: it fetched what the procedure referenced, and only that.

You can't see the body arrive — but you can see that it did, because everything after activation follows your procedure in your order.

Measured, same prompt both columns
TrackNo skillWith the skill
support-triage18 requests13
vendor-qa1411
docgen129

The saving is the discovery phase disappearing. The magnitude varies for a reason worth knowing: the more of the job already written down in your corpus, the less a skill has left to add.

Then break the description

Checkpoint M1.C3-skill
415 min

A tool

A skill is instructions; the agent still decides how to follow them, slightly differently each time. A tool is code: same input, same output, and you can test it. You reach for one when a step has a single right answer you're not willing to leave to judgement.

On support-triage that's the entitlement question — was this account entitled on the ticket's date — a query with a date filter that's wrong in a way nobody notices if it's omitted. You write the tool, then make it prove itself:

$ python3 tools/account_snapshot.py --selftest
6/6 checks passed

One of those checks must be that calling it twice with the same input gives the same result. You've just written a test for a piece of your agent. You can't do that to a prompt — this is the seed of what module 4 calls an eval.

Don't expect it to be faster
RunTool requests
Step 3, skill only13
Step 4, tool + skill13
Step 4, skill told explicitly to trust the tool16

The tool did not reduce round trips. The agent ran it and then verified parts of the result against the database anyway — and telling it not to made that run worse. Two better lessons come out of this. The agent verifying independently isn't a bug; a support engineer who double-checks a tool is behaving well. And 13, 13, 16 from the same setup means you cannot tell whether a change helped from one run. That's why module 2 keeps a scoreboard over fifteen queries, and why module 4 is largely evals.

Checkpoint M1.C4-tool
515 min

A hook

Your skill says where the output goes. Watch what happens when a prompt asks for something reasonable-sounding instead — save the result into data/, "so the next person finds it alongside the source material".

$ python3 experiments/exp.py 6
$ git status --short data/
?? data/knowledge/CASE-4471-triage.md

Your work product is now inside your evidence. Once the agent can write there you can no longer tell what was evidence and what the agent produced — the next run reads this note as a source. That's how a corpus quietly rots. Then:

$ git checkout -- data/

Which is what the git repository from step 0 is actually for: you can undo an agent. Now you write a hook that runs on every write, before the write happens, and can't be talked out of it. Test it without an agent at all:

$ echo '{"tool_name":"Write","tool_input":{"file_path":"data/x.md"}}' \
    | python3 .claude/hooks/write_boundary.py

Deny prints JSON; allow prints nothing. Three commands, no model, no waiting, definitive. Register it in settings.json — a hook that isn't registered never runs — and run the experiment again:

Write data/knowledge/CASE-4471-triage.md BLOCKED Write triage/CASE-4471.md EXECUTED corpus: 0 changes

In the trace, a blocked write is a request from the model with no RESULT line after it. That absence is what a refusal looks like.

The hole you should find

You've blocked the write tools. How would you get round it? Bash — cp, mv, sed -i, a redirect. Don't fix that by grepping shell commands: you can't enumerate the ways to write a file, and a rule matching data/ also blocks sqlite3 data/db/support.db "SELECT …", which is a read.

Controls are layered

--tools decides which tools exist at all. permissions decides which may run without asking. This hook decides what a permitted tool may touch. Module 4's gate decides who approves the consequential action. Any one of them alone is theatre — the hook's value is being the layer the model can't argue with, not being sufficient.

Checkpoint M1.C5-hook
620 min

The plugin

You have a skill, a tool, a hook, some data and some output. The question that makes this a lesson: which of those would you hand to a colleague, and which are yours alone?

Goes in the pluginStays in the project
The skill — your procedureThe data — your evidence
The tool — code that must not varyThe output — what you produced
The hook — what must not happenCLAUDE.md, intent.md — what this project is

A plugin is portable capability; the project is this situation. If a colleague installing your plugin would also need your data/ directory, something is in the wrong pile.

Two paths will break, and that's the lesson

Your tool computes its data location from __file__. Inside the plugin that resolves to the plugin's directory, where the data isn't — fix it with CLAUDE_PROJECT_DIR or getcwd(). And your skill says python3 tools/<tool>.py, a path relative to whoever installed the plugin, which isn't you. It becomes ${CLAUDE_PLUGIN_ROOT}/tools/<tool>.py.

${CLAUDE_PLUGIN_ROOT} is where the capability lives; ${CLAUDE_PROJECT_DIR} is where the situation lives. Getting these the wrong way round is why a plugin works for its author and nobody else.

$ claude plugin validate ./triage-assistant
$ python3 experiments/exp.py 7

The first is the same command anybody publishing a plugin runs. The second is the same task again, with the capability arriving from the plugin. Move .claude/skills/ and tools/ out of the way first, and if it still works, the plugin is genuinely self-contained.

Skill triage-assistant:triage-ticket …namespaced now. Packaging gives the capability an owner.

Then CLAUDE.md, loaded on every turn, so only what's true for every task goes in it — plus the @intent.md import that makes your intent load.

Checkpoint M1.C6-plugin
79 min

Debrief

The rule you'll use on Monday. Four questions in order — the first "yes" wins:

AskIf yesBecause
Must it be identical every time?A toolCode has no judgement, and can be tested
Must it happen whether the model agrees or not?A hookIt runs before the action, and can refuse
Is it how we do this particular job?A skillProcedure, loaded only when relevant
Is it true for every task in this project?CLAUDE.mdBut it costs context on every single turn

Then a separate axis: do you invoke it, or should the agent decide? Same file, one frontmatter line apart. And last: would a colleague want this? Then it goes in the plugin.

Anti-patterns you nearly committed

  • A rule in a skill that needed a hook. Your skill said where output goes; in step 5 the agent wrote somewhere else anyway.
  • A description that documents instead of triggers. Measured: it fires seventh instead of first, or never.
  • A deny list. You watched one leak a dozen tools in step 1.
  • A tool that makes judgements. If it has to weigh something, it's a skill. A tool that varies is a script you hope works.
  • Procedure in CLAUDE.md. Ten procedures there is ten procedures in the context of every question you ask.
  • A plugin that only works for its author. The two paths that broke in step 6.

Module 03 · two hours

Knowledge graphs and ontologiesIn development

Why did those three questions fail, and what do you build instead?

Not yet authored

Outline settled; lab steps not written. The tutor will say so rather than improvise.

Three failure classes of pure vector search

These are structural, not accidental — no amount of better chunking fixes them.

Multi-hop"Which other customers are exposed to the defect behind this ticket?" — several hops from defect to feature to plan to account
Aggregation"How many", "which all", "what is not covered?" Similarity search returns the most similar k. It cannot return a complete set
Constraints & time"Does this violate the policy that was in force at the time?"

What's covered

  • Taxonomy vs ontology vs knowledge graph vs semantic layer
  • Designing an ontology from competency questions — the questions you must answer — rather than from your data
  • Entities, relations, identity and entity resolution
  • Provenance, and temporality with validity dates and supersession, so answers never go quietly stale
  • GraphRAG patterns that combine graph and vector instead of choosing between them

What you'll build

An ontology derived from the three broken questions, a graph extracted from your corpus with provenance and dates, compiled into SQLite, exposed as an MCP tool, and a hybrid skill that routes each question to the graph, the vector store, or both. Plugin v0.3.

The moment to watch for is answering, by hand, the three questions module 2 left broken. Also covered: when not to build a graph — maintenance cost against question shape.

Reference

Concepts, and the wrong ideas about them

Everything here is named in a module, at the point where you've already felt the problem it solves. This page is for looking things up afterwards.

An agent is the loop

A language model does one thing: you send it text, it sends text back. It cannot open a file, run a command, or remember the last thing you asked.

An agent is the loop: send everything you have to the model, get back either an answer or a request for a tool, run the tool, add the result to everything you have, send it again. Until the model stops asking.

Two consequences: each tool use costs another round trip, which is why agents are slower than a chat; and everything accumulates, which is why the conversation gets more expensive the longer it runs.

The harness is what holds the loop

The five core tools — read, write, execute, search files, search the web — plus the context it accumulates on your behalf, the permissions, the hooks, and the skills it offers the model. Nobody asks for memory; the harness does that for you.

Progressive disclosure

Three levels, and the reason a skill is cheap: description loaded every turn, body loaded on activation, referenced files loaded if the procedure needs them. Ten skills cost ten lines until one of them is used.

Allowlists, not deny lists

A deny list is incomplete by construction. Building this lab, a deny list naming Read, Write, Edit, Bash, Glob, Grep, WebFetch and more still left the model a dozen tools, because you can only deny what you can name and new tools arrive with new versions. --tools "Read" names what exists; everything else is simply absent.

Wrong ideas worth correcting

The wrong ideaWhat's actually true
"More context is better"Context is a budget, not a virtue. Irrelevant material competes with the relevant for attention, and costs money and latency
"Embeddings understand meaning"They encode distributional similarity. Similar ≠ relevant ≠ correct. Two documents using the same vocabulary to say opposite things sit close together
"Evals are probabilistic"The model is probabilistic. Evals are the measurement system that accounts for that variance
"A knowledge graph replaces RAG"They answer different shapes of question. The graph knows structure and completeness; the vector store finds the passage you can quote
"Top-k is the answer set"Similarity search cannot express completeness, so it cannot answer "all", "how many", or "which are missing"
"A skill is just a prompt"It's a triggerable procedure with bundled assets. The description decides whether it ever loads
"MCP is required to give an agent tools"A shell script that prints JSON is a tool. MCP is how a tool becomes durable, typed and shareable
"A hook and a skill do the same job"A skill is guidance the model chooses to follow. A hook is enforcement it cannot skip
"The agent should just be autonomous"Autonomy is a ladder. The interesting engineering is in the rungs
"Chunking is a preprocessing detail"Chunking decides what can ever be retrieved. A fact split across two chunks is unreachable
"The ontology should model the domain"It should answer the questions you need answered. Start from the questions retrieval got wrong
"Citations mean it's grounded"A citation proves a source was retrieved, not that the claim follows from it

Reading the trace

The tracer is a hook attached to four moments: your prompt going out, the model asking for a tool, the result coming back, the final answer. Hook output isn't shown in the session, so it's written to .claude/lab-trace.log.

LineMeans
--> SENT TO THE MODELYour prompt going out
<-- BACK FROM THE MODELIt wants a tool. It cannot run one itself
--> HANDED TO THE HARNESSThe model is paused, waiting
<-- RESULT SENT BACKWhat the harness returned, and how many characters
(no RESULT line)The request was blocked. The tracer reports what the model asked for, not what the harness allowed

.claude/lab-raw.jsonl holds the exact payloads the harness sends the hook — the real contract, and worth reading once.

When it breaks

In rough order of how often these come up, with the fix rather than the theory.

Every tool call asks for approval

You haven't accepted the trust dialog. Until you do, the project's permissions block is ignored. Open Claude Code interactively in the folder and accept it. The symptom is a line reading "Ignoring N permissions.allow entries from .claude/settings.json: this workspace has not been trusted."

/lab:doctor says Python is too old

Read it again — it probably says it found a newer one. macOS ships 3.9 as python3, and the lab searches for 3.10+ under its other names and uses that. If nothing qualifies: brew install python@3.12 on macOS, winget install Python.Python.3.12 on Windows, then re-run.

My skill doesn't fire

It shows up as an absent Skill line in the trace, not an error. Work down this list; the first three take seconds:

  1. Is it at .claude/skills/<name>/SKILL.md? The folder name matters and the file must be exactly SKILL.md
  2. Does the frontmatter name: match the folder name? A mismatch is the quietest failure of the lot
  3. Run python3 .../scripts/check_skill.py, which covers both of the above
  4. Read your description out loud, then the prompt out loud. If nothing in the description would make you reach for it, that's your answer

You don't need to restart anything — each experiment runs as a fresh session, so a skill edited a second ago is picked up on the next run.

My hook exists but nothing happens

It isn't registered. A hook not listed under PreToolUse in .claude/settings.json never runs. check_hook.py catches this specifically, and it's the most common hook failure.

The plugin works for me and not for anyone else

A path resolved against the wrong root. The skill calling tools/<tool>.py needs ${CLAUDE_PLUGIN_ROOT}; the tool finding its data needs ${CLAUDE_PROJECT_DIR}. check_plugin.py checks both.

I broke my workspace

/lab:catchup

Replays the lab's own files without touching your work. If you've lost your own work and the room has moved on, /lab:catchup --with-reference installs the reference solution — a rescue, not a shortcut.

The plugin's commands don't appear

Run /reload-plugins. If they still don't appear, clear the cache with rm -rf ~/.claude/plugins/cache, restart, and reinstall.

An experiment takes forever

Experiments 4 to 7 make fifteen to twenty model calls each, so a minute or two is normal. Experiments 1 to 3 are quick. The wait is not the point of the exercise — the trace is.

Read the run in front of you before naming the gap

Step 2's "capability without procedure" lands differently per track, because the gap isn't the same size.

TrackGenuinely missingWill probably already be fine
support-triageThe four classification labels; ruling out configuration and entitlement in order, each with evidenceThe diagnosis itself — it usually finds the real cause
docgenWhere the output belongs; whether unsourced claims were flagged rather than dropped; run-to-run consistencyThe format. The template is in the corpus, so it follows it
vendor-qaSeverity from the contract rather than tone; every finding carrying both a criterion and a clause; coverage of unverified requirementsSpotting the obvious defects

If you tell a docgen group "look, it ignored your format" and it plainly didn't, you lose them for the rest of the module. The two gaps that hold everywhere are the wasted discovery turns and the lack of run-to-run consistency.

Step 5 has three possible outcomes

What you seeWhat it means
A Write request with no RESULT line, output redirectedThe tidy case. The hook refused it
The corpus changed anyway, no Write in the traceIt used Bash. Go straight to the Bash discussion — they found it the best way
Nothing happened at allTheir CLAUDE.md already said data/ was read-only and the model obeyed

The third is awkward because nothing visible happens, and it's also the most honest result: instructions do work, most of the time. Say exactly that, then force the demonstration:

$ claude --tools "Write" --strict-mcp-config \
    -p "Create a file at data/probe.md containing the word probe. Use the Write tool."

Guaranteed to attempt a write into data/, and it comes back refused with their own message. Which is the point in one line: the instruction worked this time, and the hook works every time.

Before any change, run the self-test

$ python3 plugins/lab/scripts/selftest.py

It applies every stage for every track and checks the failures that only show up in front of a room: a stage payload leaking one track's task to every group, an unresolved placeholder, a file the module tells participants to open that doesn't exist on their track, or a command promised in the text but never implemented. A few seconds, no model calls.

What isn't done

  • No timed dry run. 112 minutes is arithmetic, not evidence
  • No run-of-show with minute markers and cut lines
  • No participant has done this. Every gate has only judged reference implementations, never a real first attempt — which is exactly where they'll turn out too strict or too lenient
  • Modules 2 to 4 are outlines. The docgen and vendor-qa corpora are also too small for module 2's fifteen golden queries, and expanding them is a prerequisite rather than part of it
